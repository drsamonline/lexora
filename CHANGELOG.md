### Added
- 2026-10-29 — Session 44 (**dependency licence review for the GUI extra**; ADR-0009's open item gets an answer short of a decision):
  - **`docs/DEPENDENCY_LICENCE_REVIEW.md`** — reads LGPL-3.0 §4 against PolyForm Noncommercial and finds **no licence conflict**: LGPL requires relinkability (satisfied by the shared-library wheels) plus notices, and PolyForm restricts commercial use, not modification. It bounds the exposure to the optional `[gui]` extra, since the core install stays Qt-free (ADR-0008 decision 1).
  - **The finding that could actually bite:** PySide6's own licence is only half the story — the wheels bundle individual Qt modules and some are GPL-3.0-only. The review therefore audits what the GUI imports (`PySide6.QtCore`, `QtGui`, `QtWidgets` and nothing else, lazily, all in `app.py`) rather than trusting the toolkit name, and says plainly that the module-to-licence mapping must be re-confirmed against the wheel at packaging time (PySide6 is not installed in the review environment, so this was read from source, not from a wheel).
  - **A shipping checklist** (§4): NOTICE file, LGPL+GPL texts beside `LICENSE`, the LGPL notice reachable from the About view, a documented relinking route, and re-verification whenever PySide6's version moves. Wired into RELEASE_PROCESS R3 as an open sub-item.
  - **Four options for the owner** (§6): comply and ship (recommended if the GUI ships at all), process separation, drop `[gui]` from distribution, or a commercial Qt licence — the choice to be recorded as ADR-0010. PyMuPDF's AGPL flag from ADR-0006 is restated as unchanged and still not a dependency.
  - Explicitly **not legal advice**, and it says so: the owner remains accountable, and a lawyer's read is warranted if the GUI is ever distributed commercially.
  - Cross-referenced from ADR-0009 Consequences §3, the docs index, and RELEASE_PROCESS R3.

### Fixed
- 2026-10-29 — Session 43 (**provenance checkpointing was lossy; add `corpus-reconcile`**):
  - **Bug:** the per-file checkpoint added in Session 42 rebuilt the record from the *current* invocation's progress, so an interrupted invocation **shrank** the record of files that were still on disk. Observed live: two killed passes left 587 texts / 287.9 MB on disk recorded as 232 files. Checkpoints are now **supersets** — prior records are seeded in and only the file just processed is upserted, while a genuine failure removes that file's record (the manifest must never cite a missing text).
  - **`corpus.reconcile_snapshot()` + `harness.py corpus-reconcile --root DIR`:** repairs a truncated record from the bytes on disk, without the network and without re-walking 1400 ids. Files whose id is outside the requested set are counted as `orphaned` and deliberately not claimed as corpus members. On the real snapshot: 166 records recovered in 12 s, record brought to exact agreement with the disk (587 files, 287.9 MB).
  - **Checkpoint cadence** is every 25 files instead of every file — the sidecar grows to hundreds of KB and per-file rewrites dominated a mostly-reuse pass (~0.8 s per id). A kill can now lose up to 25 recent entries, which is precisely what `corpus-reconcile` repairs.
  - Provenance for `gutenberg-cat-partial` re-committed at 587 files / 287.9 MB (`reconciled: true` on the 166 rebuilt entries). **≥1 GiB still unmet** — fetch time, not machinery.
  - Tests: 7 new in `tests/test_corpus_reconcile.py` (recovery from disk, idempotence, orphans not claimed, byte-stable sorted output, checkpoint-superset invariant, failure-removes-stale-record, shared sidecar writer). Suite **245 → 252 passed**, 1 skipped.
- 2026-10-29 — Session 42 (**catalog-driven corpus selection; fetch made resumable** — P2/OQ-8 groundwork):
  - **`corpus.select_ids_from_catalog()`** derives ids from Project Gutenberg's official catalog (`pg_catalog.csv`, 21,271,171 B) instead of a hand-curated list: keep `Type=Text` + `Language` containing `en`, order by PG id ascending, take `--catalog-limit`. Ordering by id means the selection grows at the end rather than reshuffling when the catalog is regenerated, so a snapshot can be resumed. The catalog's SHA-256, the filter, the order and the limit are recorded in the snapshot's `selection` block — same digest + same filter ⇒ same id list.
  - **`corpus.fetch_catalog()`** caches the catalog under the gitignored `corpus/_catalog/`; **`harness.py corpus-fetch --catalog-limit N [--catalog-cache DIR] [--exclude-ids …]`** wires it up.
  - **Fetch is now resumable.** `fetch_gutenberg_snapshot` checkpoints its three sidecars after every file, with `complete: true/false`. Previously they were written only at the end, so an interrupted fetch left texts on disk with no provenance record and the next run re-downloaded all of them. Verified live: 210 of 317 files reused on the third invocation.
  - **First bulk snapshot recorded:** `benchmarks/provenance/gutenberg-cat-partial/` — 1400 ids selected from catalog `3cece81a…`, **317 files / 165.3 MB** fetched, 29 failures recorded rather than hidden, `complete: false`. Manifest `a2af8ae9…` verifies with 0 problems; splits 215/38/65 with no lineage straddling. ≥1 GiB remains unmet (fetch time, not machinery).
  - **Rights caveat documented in CORPUS_POLICY.md, not glossed:** the catalog has no rights column, so bulk selection inherits Gutenberg's US-public-domain posture plus each file's own licence statement; a per-item RDF rights check is an open item.
- 2026-10-29 — Session 41 (**streaming decode — P1-T8 closed**; the last open memory item from P1):
  - **`container.unpack_stream()` + `read_index_stream()`**: the decoder validates the index up front (header, trailer, index checksum, offsets, limits — same rules as `read_index()`, shared via `_read_index_parts()`), then decodes one block at a time and writes it only after its SHA-256 matches. The resident set is the index plus one block, instead of the whole archive plus the whole output.
  - **Measured effect:** decode peak RSS **34.8 MiB at a 32 MiB archive and 34.1 MiB at 64 MiB** (flat) versus 116.1 MiB / 188.6 MiB on the buffered reader — the 256 MiB decode budget in PERFORMANCE_BUDGET.md is no longer reachable through archive size. `benchmarks/results-rss-core.json` rows now carry `decode_path` so the two readers stay distinguishable.
  - **CLI:** `unpack` streams by default; `--no-stream` keeps the old path for A/B evidence runs; `--meta` reads only the index (no block decoded) and reports `verified=index-only` on stderr. The refusal guarantee is unchanged and is now tested explicitly on stdout: the payload is staged in a temp file, so a corrupt block emits **zero bytes** to `--out` or stdout.
  - **Tests:** 37 new in `tests/test_unpack_stream.py` (byte-identity with `unpack()` across 7 sizes × 3 block sizes, golden vector, index parity, `only_block` parity and range refusal, corrupt block/header/truncation refusals, non-seekable source, CLI stream-vs-buffered identity, stdout silence on corruption, no temp-file leakage). Suite **201 → 238 passed**, 1 skipped.
