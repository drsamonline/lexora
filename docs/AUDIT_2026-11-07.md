# Audit — lexora vs ziptastic, 2026-11-07

**Scope.** Read the lexora tree at `cc7317d` and the ziptastic tree at `030c456`
in full at the level of source and load-bearing docs; ran the test gate before and
after; verified every claim below against code or an artifact, not against the
project's own documentation. This is an audit *of the repository as it is*, so
where a doc and the code disagree, the code wins and the doc is listed as a finding.

**Result in one line.** The code is in better shape than its documentation: the
integrity story (validate-before-allocate, per-block SHA-256, determinism) holds up
under reading, the gate was green at 514 tests, and the four real defects found were
all of one kind — a hard-coded zstd assumption or a stale default — not a broken
guarantee. All four are fixed in this change.

| | before | after |
|---|---|---|
| Gate (`PYTHONPATH=src:. python3 -m pytest -q`) | 514 passed, 1 skipped | **540 passed, 2 skipped** |
| Codecs the reader can decode | 1 (zstd), hard-coded in 5 places | 2, through one registry |
| New tests | — | 27 (26 codec/dispatch/default-drift, 1 real-binary skip) |

The second skip is the real-ziptastic round trip: the binary is not vendored and
cannot be built in this environment (no cmake/ninja/g++), so that test reports why
it skipped rather than passing vacuously.

## Findings

Severity is about consequence, not effort: **High** would mean a wrong or unsafe
archive, **Medium** means misleading metadata or a latent inconsistency, **Low** is
cosmetic.

### F1 — The header names a level the archive did not use (Medium, open)

`CODEC_ID_ZSTD = "zstd-raw-l19"` is frozen into every header (ADR-0007), but
ADR-0012 moved `DEFAULT_LEVEL` to **9** in Session 53 and nobody revisited the id.
Verified live:

```
DEFAULT_LEVEL        : 9
header codec_id      : zstd-raw-l19
zstd_core profile@9  : zstd-raw-l9      <- the same archive, reported differently
```

Two consequences. A level-9 and a level-19 archive carry the **identical** header
id, so `inspect` / `--meta` report a level that was not used and a reader cannot
tell the two apart. And `zstd_core._profile_id()` disagrees with the container for
the same bytes, because `zstd_core` carries its own `DEFAULT_LEVEL = 19` — two
constants with one name and different values.

Not fixed here, deliberately: `codec_id` is a frozen format field, so changing the
string is a reader-visible format change that needs its own ADR and a tolerance
decision for archives already written. The three honest options are (a) rename to a
level-neutral `zstd-raw` under a new ADR, (b) keep the id and record the level in a
spare header byte, (c) accept it and document that the id is a *codec family*
label, not a level. **Recommendation: (a) at the v0→v1 boundary, with the level
also written to a field that has room for it.** Until then, no tool should read a
level out of `codec_id`.

### F2 — The GUI's codec defaults were still level 19 (Medium, fixed)

`AppService.run_compress(level=19)` and `AppService.run_pack(level=19)` kept the
pre-ADR-0012 default while the library, the CLI and `DEFAULT_SETTINGS` all said 9.
This is precisely the drift ADR-0012 was written to end, and the regression test it
shipped only inspected `DEFAULT_SETTINGS` — so a green suite said nothing about it.
Fixed to `DEFAULT_LEVEL`, with a test that reads both signatures.

The latent risk was real rather than theoretical: the widgets pass an explicit
level today, so the default was dead code, but any new caller (and the batch queue
that ADR-0011 still has to build) would have inherited 19.

### F3 — "The container is codec-agnostic" was true of the layout, not the code (Low, fixed)

`codec_id[16]` is in the header, and `ZIPTASTIC_NOTES.md` correctly says a codec
swap is "the smallest possible change". But zstd was hard-coded in five places:
`_build_header` wrote the id, `_validate_header` accepted only that id, and
`unpack`, `unpack_stream` and `verify_stream` each compared the frame prefix
against a literal `b"\x28\xB5\x2F\xFD"`. A codec swap was a claim, not a switch.

Fixed by a registry (`src/lexora/codec_registry.py`) that owns the name→id→
implementation mapping and the per-codec frame magic. `container.py` no longer
names a codec anywhere. The reader's accept-list is still closed — an unknown id
remains a hard `E-CMP-006` refusal, which is the property that mattered.

### F4 — A bounded decode mislabelled its block (Low, fixed)

`unpack --block N` enumerated the *selected* list, so any failure inside a bounded
decode reported `block 0` regardless of `N` — in exactly the case the flag exists
for. Fixed to carry absolute indices; test added.

### F5 — The documents disagree with each other and with the code (Medium, partly fixed)

Not one stale sentence but a pattern, and the pattern is the interesting part:

- `NEXT_SESSION.md` still lists "**Owner decision — the CLI's default encode level**"
  as open. It was closed by ADR-0012 in Session 53.
- `ZIPTASTIC_NOTES.md` said "lexora's Phase-1 backend is **zstd-19**". It is 9.
- `STATUS.md`'s own header says "**Last verified:** 2026-10-29 (Session 41 …)" while
  the same file's health row says "measured **2026-11-03**". Both cannot be the
  last verification.
- `SESSION_LOG.md` ends at **Session 69 (2026-10-29)**, yet `STATUS.md` records a
  2026-11-03 verification and the R4/R5 artifacts post-date the log's last entry.
  The work of that gap has no session record.
- `ZIPTASTIC_NOTES.md` also repeated ziptastic's **−11.83 %** headline without the
  qualifier that it is a 10-file subset (see the comparison section below).

Corrected here: the notes file (level, subset qualifier, what has now landed) and
the next-session card. Left open: the STATUS header and the log gap, because
reconciling twenty sessions of trail is a session of its own — it is now the top
housekeeping item rather than an untracked background problem.

### F6 — What held up under reading (no action)

Recorded because an audit that lists only faults is not an audit:

- **Validate-before-allocate is real and in the right order**: magic → header
  checksum → major → must-understand flags → codec id → declared limits against
  the LIM-01/LIM-02 *ceilings* (not just against themselves, which was Session 54's
  fix) → minimum file size. Every refusal happens before a decode or an allocation.
- **Per-block integrity is per-block**: an index of `(offset, compressed_size,
  uncompressed_size, sha256)`, a hashed trailer over the index, and a per-block
  SHA-256 check before any byte is written. A corrupt block costs that block.
- **Determinism is tested, not asserted**, at both the codec and the container level.
- **No network, no telemetry, no `shell=True`.** The only subprocess in the package
  is the optional codec adapter added here, and it passes an argument list.
- **The refusal paths are the tested paths** — `E-CMP-006`, `E-INTEGRITY-001`,
  `E-RES-004` all have negative tests, which is why F3's five hard-coded sites were
  the *only* place a second codec could hide.

## lexora ↔ ziptastic: what actually transfers

Both repos were already cross-reviewed (`lexora/docs/ZIPTASTIC_NOTES.md`,
`ziptastic/docs/LEXORA_ASSESSMENT.md`). The useful work here was to check those
notes against the current trees, because one headline had drifted out of context.

### The correction that matters

The notes present **−11.83 % vs `xz -9`** as a Silesia result. It is, but it is a
**10-file, 119,259,397-byte subset** of a 12-file, 211,938,580-byte corpus — and
the two excluded files are the two largest: **`webster` (41 MiB, a dictionary) and
`mozilla` (51 MiB, binary)**, both unmeasured because they exceed ziptastic's
300 s per-command limit at every block size tried.

Two things follow. The good news is that the measured subset is *weighted toward
text*, which is lexora's corpus class: `reymont` −22.2 %, `mr` −18.2 %,
`osdb` −17.6 %, `xml` −17.3 %, `dickens` −16.8 %, `nci` −16.7 %, `x-ray` −15.4 %,
`ooffice` −14.1 %. The caution is that the win is **concentrated, not general**:
`samba` −0.64 % and `sao` −0.001 % are binary files where CHCE is level with `xz`.
And the largest *English text* file in the corpus is the one nobody has measured —
a dictionary is close to a worst case for a word-model, so it is the file most
worth measuring before any default changes.

### What to take, ranked by evidence

1. **The codec itself — taken (ADR-0014).** It is the only change in either repo
   that moves the number the product exists to move. lexora's R5 is +0.77 % *worse*
   than `xz -9` and cannot improve by tuning zstd; CHCE is −11.83 % under `xz -9` on
   a text-heavy subset. The gap between those two facts is the entire opportunity.
2. **The negative-results discipline — taken as practice.** ziptastic's
   "measured and closed — do not revisit" table (delta preprocessing +1.7…+91 %
   worse; byte-shuffle +4.8…+27.6 % worse; LZP −0.02…+1.9 %; word dictionary
   −0.38 % on English but **+0.93 % on Polish**) is why lexora should not build a
   word-dictionary stage. That is a week of work saved by a table.
3. **The transferable rule**, now written into the notes in ziptastic's own words:
   *a transform pays only if it removes redundancy the backend cannot already
   capture.* It explains every negative result in both repos, and it predicts that
   CAN-R01 (encoding → UTF-8) will *hurt* compressed size for non-ASCII text while
   being correct for lexora's stated purpose. Those are different objectives and
   the docs now say so instead of implying one.
4. **Not taken, and worth saying why**: ziptastic's format-aware transforms
   (preflate/ZIP, JPEG, GIF, BMP, CD-ECC, SQLite) target *containers*. lexora's
   input is text. Porting them would be building the sibling's product inside this
   one; the honest path is to call the sibling.

### What goes the other way

lexora's three patterns that ziptastic's own assessment says it should copy —
validate-before-allocate, per-block integrity with an index and trailer, and
determinism as a stated guarantee — were all confirmed present and tested here. No
action for lexora; that direction is ziptastic's queue.

## Remaining work, in the order I would take it

1. **Measure CHCE on lexora's own corpus, through the new seam.** This is the
   decision input for `codec_registry.DEFAULT_CODEC` and the only way to know
   whether the Silesia effect transfers. Blocked here: the ziptastic binary needs
   cmake + ninja + g++ and 23 vendored submodules, none of which exist in this
   environment. **Needs a build machine, then
   `lexora pack --codec ziptastic` on the R5 corpus at the protocol block size.**
2. **Decide F1** (the codec_id string) before the v0→v1 boundary, while there are
   still few enough archives in the world for a rename to be cheap.
3. **`.lxdb` byte layout (ADR-0013).** Gated, not blocked: the corpus half of G2 is
   met at 1.014 GiB; what is missing is a protocol-scope benchmark run plus owner
   sign-off. The new codec changes the calculus slightly — an `.lxdb` of CHCE
   members is a different size/speed point than one of zstd members.
4. **GUI process separation (ADR-0011 implementation).** Needs a Qt-capable
   machine. The `run_compress`/`run_pack` defaults are now consistent, so this work
   starts from a clean base rather than inheriting a wrong default.
5. **Documentation reconciliation (F5).** STATUS header, the Session-69→now log
   gap, and the DECISIONS/IMPLEMENTATION_MATRIX rows for the new codec.

## Method notes

Every number above was produced in this environment: the gate was run before and
after (`514` → `540` passed), the codec-id disagreement was printed from a live
`pack()` (F1), and the Silesia figures were read out of `docs/BENCHMARKS.md` at the
"Corpus refresh" table rather than from any summary of it. Wall-clock and
throughput figures are **not** quoted from this box: it is a 2 vCPU container, and
this project's own PERFORMANCE_BUDGET already says such numbers are not quotable.
