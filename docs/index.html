What it is

Clean conservatively. Compress exactly.

LEXORA ingests text, canonicalizes it into deterministic UTF-8 bytes, and then compresses those bytes with a guarantee that holds for every input: the decompressed stream is byte-identical to the canonical stream. The core invariant is deliberate — canonicalization may lose information relative to the original source; compression after canonicalization must never lose a single byte.

Byte-exact losslessness

The round-trip is verified before anything is written: decode(encode(C)) == C. A failed comparison is a blocker, not a warning.

core invariant

Conservative canonicalization

Versioned, deterministic rule set (lexcan-0.1: CAN-R01/R02/R05) with golden test vectors and a whitelist contract — non-matching bytes pass through unchanged.

versioned rules

Cost-driven selection

Candidates compete against pinned baselines under a total-serialized-byte cost model — every byte of header, index and payload counts, not just the compressed stream.

measured, not assumed

.lxz v0 container

Frozen v0 layout per ADR-0007: 128-byte header, one complete zstd frame per block, per-block SHA-256, 40-byte trailer. Every block is decode-verified and the write is atomic.

experimental · major 0

A real CLI

Five tested subcommands — canon, zround, pipe, pack, unpack — with a stable exit-code contract (0, 2–7) exercised by the test suite.

canon/zround/pipe/pack/unpack

Built for low resources

Designed to run within a ~4 GiB RAM budget using bounded, streaming/block-based processing. Multilingual coverage (English, Hindi, Gujarati) is a design target.

bounded blocks
How it works

A pipeline with one hard boundary

Extraction and canonicalization are allowed to be lossy relative to the source. Everything after the canonical bytes exist must round-trip exactly. That boundary is where the guarantee lives.

01

Ingest

TXT/PDF files; OCR optional for scanned pages. (file ingestion planned)

02

Canonicalize

Versioned, deterministic UTF-8 bytes. may be lossy vs source

03

Compress

Cost-selected codec; candidate vs pinned baselines.

04

Verify

decode(encode(C)) == C enforced before writing.

05

Archive

.lxz v0 container now; .lxdb planned.

Quickstart

Install from a source checkout — no published package exists yet.

bash — install & verify
# editable install (Qt-free core)
pip install -e .
# + test suite, or + experimental PySide6 GUI
pip install -e ".[dev]"
pip install -e ".[gui]"

python3 -m pytest -q   # 192 passed locally
lexora --help          # lexora 0.0.1.dev1

Run the pipeline

canonicalize → compress → verify, then pack into a container.

bash — end-to-end
# raw → canonical → zstd frame → verify
lexora pipe --in raw.txt --out out.zst

# or step by step
lexora canon  --in raw.txt --out canon.txt
lexora zround --in canon.txt --out frame.zst

# wrap canonical bytes into .lxz v0
lexora pack   --in canon.txt --out archive.lxz
lexora unpack --in archive.lxz --out back.txt
Exit codes are part of the contract: 0 success · 2 usage · 3 I/O · 4 canonicalization · 5 codec · 6 round-trip failure · 7 container refusal. A round-trip mismatch (6) is a blocker severity.

What you get

  • canonicalize.py — conservative v0 rule set with golden vectors
  • zstd_core.py — frame codec with round-trip verification
  • container.py — .lxz v0 pack/unpack (ADR-0007)
  • cli.py — the five-subcommand CLI with stable exit codes
  • benchmarks/ — harness + frozen corpus manifest

No releases, no download artifacts, and no coverage/release badges exist — those claims are not yet true.

FAQ

Straight answers

Q01Is LEXORA released or production-ready?
No. It is a Phase 1 prototype in development with no stable API and no releases. Early implementation code exists (canonicalization, a Zstd core baseline, the .lxz v0 container, a benchmark harness, a CLI, and experimental PySide6 GUI milestones).
Q02Does LEXORA beat Zstd, Brotli or XZ?
No validated evidence exists either way, and the project says so explicitly. The only published numbers are baseline-vs-baseline on a Tier-1 smoke corpus. Claiming any advantage before reproducible benchmark evidence would be out of scope by design.
Q03What exactly does "byte-exact" mean here?
For the canonical byte stream C, the guarantee is decode(encode(C)) == C for every input. It is enforced at build time — a mismatch is treated as a blocker (exit code 6), not a warning.
Q04Can canonicalization lose data?
Yes — by design, and conservatively. Canonicalization may be lossy relative to the original source (for example, encoding normalization and line-ending normalization). The hard rule is that compression after canonicalization must never lose a byte. Reconstructing original OCR output or PDF layout bit-for-bit is an explicit non-goal.
Q05Which languages and inputs are supported?
Design targets are .txt and .pdf (text layer first, OCR optional for scans) across Latin, Devanagari and Gujarati scripts. Current reality: byte-level canonicalization of raw text streams is implemented; TXT/PDF file ingestion is not implemented yet, and the build scope is English-only, with Hindi/Gujarati deferred (not blocking).
Q06What is the licence, and who maintains it?
MIT © 2026 Dr. Sohil Momin, who owns the project. CI runs are currently paused by owner decision (free-tier minutes exhausted); the verification gate is local — pytest -q plus a docs link check before every commit.
